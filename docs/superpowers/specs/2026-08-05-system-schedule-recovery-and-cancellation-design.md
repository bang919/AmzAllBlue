# 定时计划恢复与取消设计

## 目标

系统计划的运行状态会持久化到 MySQL。服务异常中断、重启或正常关闭后，不得遗留永久的 `RUNNING` 状态；用户还应能主动停止正在运行的计划，并阻止该次运行继续写入本地业务数据。

## 范围

本次只覆盖“系统设置”中的系统计划：FBA 当日销量、FBA 当前库存、FBA 历史数据补齐、广告当日表现、广告近 30 天回补、关键词排名与建议竞价、广告 AI 批量分析。

不尝试撤销 Amazon、SIF 或 OpenAI 已经收到的远端请求。停止后应用会停止等待、下载和写入这些请求的结果。

## 状态模型

系统计划保持现有的 `COMPLETE`、`FAILED`、`RETRY_WAIT`、`RUNNING` 状态，并增加 `CANCELLED`。

每次执行在 `system_schedule_settings` 中记录不可预测的运行令牌。任务异步链路持有该令牌；在关键的网络请求、轮询、下载和本地写入之前确认令牌仍是当前且状态仍为 `RUNNING`。令牌不匹配或状态为 `CANCELLED` 时，任务立即停止，且不得将状态改回完成或失败。

停止操作会原子地将当前 `RUNNING` 任务更新为 `CANCELLED`，写入“用户已停止任务”原因和完成时间，并使该令牌失效。操作可重复执行：任务已经不是运行中时，返回当前状态而不修改其他运行记录。

## 取消与数据一致性

服务为每个系统计划的当前运行保存内存中的 `AbortController`。用户停止时，如果该控制器仍在本进程内，立即 abort；支持 signal 的本地请求将直接中止。

服务重启后内存控制器不存在，但数据库的令牌与状态校验仍能阻止旧异步回调覆盖已取消、已失败的状态。无法中止的外部远端任务可能仍会在供应商侧完成，但应用不会继续拉取或把结果写入本地数据库。

FBA 队列、广告报表轮询、SIF 同步和 AI 批量分析均接收相同的运行上下文，并在任何可控的持久化写入之前检查是否已取消。取消作为独立结果处理，不创建自动重试。

## 服务生命周期

启动时，统一恢复所有遗留 `RUNNING` 系统计划为 `FAILED`，消息为“服务重启，任务已中断，请重新执行”。现有广告报表队列恢复仍会将遗留 `QUEUED` / `RUNNING` 作业标为失败。

收到 `SIGINT` 或 `SIGTERM` 时，服务先停止新的计划 tick、取消当前控制器，并将所有 `RUNNING` 系统计划和正在执行的广告报表任务统一标为 `FAILED`，消息为“服务关闭，任务已中断，请重新执行”；完成数据库写入后才关闭 HTTP 服务并退出。

强制终止或断电无法保证关闭钩子运行，由下一次启动恢复兜底。

## 接口与界面

增加停止当前系统计划的 API，仅允许任务处于 `RUNNING` 时生效。响应返回最新计划列表，供前端立即刷新。

系统设置卡片在 `RUNNING` 时保留禁用的“立即执行”按钮，并显示红色“停止”按钮。停止成功后显示“已停止 · 用户已停止任务”，并恢复“立即执行”按钮。`CANCELLED` 不计为失败，不触发自动重试；下一个正常计划周期仍可运行。

## 验证

- 服务启动前人为留下 `RUNNING` 状态，启动后应变为 `FAILED`，且可立即重新执行。
- 运行任一计划后点击停止，应变为 `CANCELLED`，不允许异步完成回调覆盖该状态，也不能继续写入后续结果。
- 在运行时发送正常关闭信号，状态应为 `FAILED`；重启后不应显示“正在执行”。
- 正常完成、任务错误和现有重试策略仍应分别产生 `COMPLETE`、`FAILED` / `RETRY_WAIT`。
